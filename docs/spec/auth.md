# Authentication and account requirements

What Shell's sign-in, accounts, sessions and administration must do, each
as a requirement with a stable ID and a test. The [README](../../README.md)
owns principles and [architecture.md](../architecture.md) the mechanisms;
this file owns behaviour and values. Hostnames are examples.

## 1. Conventions and assurance

**IDs.** `AUTH-<AREA>-NNN` for functional requirements, `NFR-NNN` for
non-functional ones. An ID is never reused or renumbered; a requirement
whose meaning changes gets a new ID.

**Columns.** *Requirement*, in MUST wording. *Acceptance*, one testable
line. *Verification*: unit test; integration suite (against the real
provider, arch §13); configuration check (settings, startup checks, grants
or DNS inspected); hands-on check (by hand once its subject exists, arch
§15); load test. *Owner*: provider configuration; app (Shell's backend, web
app and console, and the mobile-client contract forks follow); sign-in
screen (our sign-in module in `web/`); operations. *ASVS*: the OWASP ASVS
5.0 requirements that clearly apply, blank if none; "To verify" marks an
uncertain mapping. "arch §n" is section n of
[architecture.md](../architecture.md).

**Words.** *Realm*: customer (subscribers) or workforce (staff). *Fresh
sign-in*: signing in again within a session, by an email code or Google
for subscribers and a passkey for staff; it sets the session's
`auth_time`. *Passkey confirmation*: a subscriber's passkey standing in for
a fresh sign-in, only where AUTH-FRESH-006 allows. *Window*: how old a
fresh sign-in may be for a route; zero means every time. *The switch*: the
account's "Require trusted devices" setting. *Trusted device*: a browser or
app install that has enrolled a device key for the account ("Trust this
device"). *Risky action*: a fork's route with a trusted-device part in its
gate; Shell defines none for subscribers. *Device record*: one entry of
"Where you're signed in", one per sign-in, named by its *sign-in ID*. 
*Reference mobile test client*: a minimal native test client for verifying
the mobile authentication contract on iOS and Android, not a production app.

**Assurance.** Subscribers sign in with an email code or Google. Both are
single factors: an emailed code is one factor, and Shell can't see a
Google account's own MFA. Accepting them at ASVS Level 2 relaxes ASVS 6.3.3
on purpose. The rationale: every subscriber account and session is treated
the same, signing in again by email code is also the way back in, and
passkeys never gate a user's control of their own account, so every
account is only as strong as its mailbox or Google account (the email
ceiling, arch §11). The mitigating controls are a fresh sign-in before any
change to how the account signs in, before logging out other devices and,
every time, before deletion (section 6); the Require trusted devices
switch, which limits risky actions to enrolled devices; the device list,
with logging out one device or all; notices on sign-ins from new devices
and on every change to sign-in methods, trusted devices and deletion; the
24-hour deletion delay and the support freeze; code rate limits; 10-minute
access tokens; and the refusal of logged-out devices' tokens. ASVS Level
3's 6.3.6, which rules out email as a factor, is out of scope. Shell claims
no NIST AAL for subscriber sign-in, and subscriber sessions follow AAL1
time limits (NIST SP 800-63B-4). Staff sign in with passkeys, with user
verification required and checked by the server, and staff sessions follow
AAL2 time limits.

**Owned elsewhere.** Token acceptance and realm hosts, arch §3; clients, the
principal, the gate mechanism and API versioning, arch §4; how the default
provider meets section 2, arch §5; data placement, tables, audit-log columns
and retention, and residency, arch §6; cookie attributes and the refresh
flow, arch §7; account-change mechanics, trusted-device keys, the device
list and continuation codes, arch §8; administration, the console's Data
section and the staff script, arch §9; the error-code scheme, key cache,
timeouts and retries, arch §10; rate-limit layers, security headers, the
threat model and the email ceiling, arch §11; environments, internal TLS,
CI/CD, the integration suite, observability, backups and key rotation, arch
§13; deployment decisions,
[README](../../README.md#deployment-decisions).

## 6. Fresh sign-ins and trusted devices

Every route declares a gate (arch §4) in two parts that it uses alone,
together or not at all: a fresh sign-in, required whatever the switch says,
and a trusted device, required only while the switch is on. Each Shell
route's gate is in the route catalogue (section 9); forks set one for every
action they add.

| ID | Requirement | Acceptance | Verification | Owner | ASVS |
|---|---|---|---|---|---|
